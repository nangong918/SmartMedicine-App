### 支付:

(支付成功之后应该mq通知订单系统取改变订单状态, 而不是在支付系统中执行, 这些应该都是异步操作.)

* 行为幂等性
  分布式锁进行行为幂等性校验:
  * 锁内容:
    dataId: userId:orderId
    mappingPath: PurchaseConstant.Pay_CONTROLLER + PurchaseConstant.AppointmentPay_API

↓

* 事务支付订单
  payAppointmentOrder
  审核内容 (数据源来自于Redis的OrderStatusAo, 不依赖订单系统的Mapper, 系统解耦):
  1. 商户是否过期 orderStatusAo.getMerchantEndTime()
  2. 订单是否过期 (**乐观锁**首次Redis检查) orderStatusAo.getCustomerStatus()
  3. 待支付检查
  4. 用户账户余额是否充足: 锁行检查用户的金额 + 扣减制定金额
  5. 支付成功后再次检查 订单是否过期 (**乐观锁**再次Redis检查):
     * 避免出现: 支付 -> ( 订单超时 -> 订单取消归还商品 ) -> 支付成功/支付失败
     * 使用乐观锁: 在支付之前检查订单是否过期, 支付成功之后标注已经支付, 并且再次检查订单是否过期, 如果过期全部回滚.
       缓存订单状态更新(在订单系统执行)
  6. 成功: Mq通知订系统 APPOINTMENT_PAY_RESULT_ROUTING -> handlePayResultMessage

↓

* 支付结果通知
  通知medicine-service, 还要避免Mq消息丢失
  * 订单状态更换
  * 解除支付分布式锁
  * netty通知前端 (Spring Event 异步)

### 缓存设计

缓存更新的方式:

* 查询数据库之前查询 Redis 适合使用 AOP：集中管理。查询数据库之前的 Redis 查询可以被视为一个横切关注点。是整体的，同步的。
* 更新数据库之后同样更新 Redis 适合使用事件驱动：使用事件驱动架构可以将数据库更新和 Redis 更新解耦，使得这两个过程之间是不直接依赖的，是异步的。
* 逻辑上: 查询数据库前先查询Redis的合理的, 但是更新数据库之后一定更新Redis是不合理的. 属于是冗余了Mapper本身的功能.
